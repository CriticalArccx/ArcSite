# ArcSite — On-site (standalone)

This is the Retool React app **ArcSite - On-site** exported to a plain Vite + React + TypeScript
project, talking directly to Supabase instead of Retool's hosted backend. It was generated by
pulling the live source out of Retool and rewriting the backend-function layer as a Supabase
client library — the UI (components, styling, behavior) is unchanged.

## What changed vs. the Retool version

| Retool version | This version |
|---|---|
| `hooks/backend/rno04.ts` — RPC hooks calling server functions in `/backend/rno04/*.ts` | `src/lib/api.ts` — the same hook names, but each one calls Supabase directly from the browser |
| `hooks/useCurrentUser.ts` — Retool's platform session | `src/lib/useCurrentUser.ts` — Supabase Auth (magic-link) |
| Server-side `req.user.email` (trusted) stamped onto writes (signoff, updated_by) | Stamped client-side from the Supabase session — only as trustworthy as your RLS policies, see below |
| Workflows/settings stored in Retool DB | Moved to two new tables in your Supabase project: `arcapp_workflows`, `arcapp_settings` (already created and migrated — see `supabase/schema.sql`) |
| Access control via Retool's `checkEditor` backend function | Same logic (`STY4authorized_editors` lookup), now run client-side + enforced via RLS |

Everything else — `STY4dropdownoptions`, `STY4BackEndData`, `STY4Assets`, `STY4RTFT`,
`STY4authorized_editors` — is unchanged; this app reads/writes the exact same Supabase project and
tables it already used inside Retool. The one exception is `STY4Submittals`: it's no longer used
at all — Submittals were reworked onto a new `arcapp_submittals` table (see below) — but it still
exists in your database untouched, in case something else reads it.

## Known gaps (things Retool was doing that this export doesn't replicate)

1. **Authentication UI is intentionally minimal.** Retool handled sign-in for you automatically;
   this version adds a Google sign-in button + a magic-link fallback (click the "Sign In" pill in
   the top bar) — see "Sign-in" below.
2. **Row Level Security on `arcapp_workflows` / `arcapp_workflow_items` is currently wide open**
   (`anon` + `authenticated`, no editor check), by request, so anyone can build/edit workflows
   without signing in. `arcapp_settings` stays editor-only. See `supabase/policies.sql` for the
   editor-restricted versions this replaced, kept commented out for an easy revert.

## Project switcher — STY4 / SAN-NT1B / RSE1A

ArcSite now supports more than one LaunchPad project. Click the site pill in the top-right (next to
Sign In) to pick between **STY4** (Phoenix DC3), **SAN-NT1B**, and **RSE1A** — the choice is saved
to `localStorage` and the page reloads, so every fetch in the app comes back scoped to the newly
picked project.

- **`src/lib/project.ts`** is the single source of truth — `CURRENT_PROJECT` is read once at
  module load (switching reloads the page rather than trying to make every hook in the app
  reactive to a live change), and every table-name template in `src/lib/api.ts`
  (`STY4dropdownoptions` → `` `${CXALLOY_TABLE_PREFIX}dropdownoptions` ``, same for
  `BackEndData`/`authorized_editors`) reads it instead of a hardcoded `'STY4'` literal.
- **CxAlloy's own project id/domain differ per site**, not just the table prefix — found while
  wiring this up: STY4's checklists/issues deep-link to `google.cxalloy.com` (CxAlloy project
  `50506`), SAN-NT1B's to `tq.cxalloy.com` (project `49639`). `cxAlloyLinkBase()` in `project.ts`
  holds both.
- **ArcSite's own tables are now project-scoped, not one shared pool.** `arcapp_settings` (PK
  changed to `(project_key, setting_key)`), `arcapp_tasks`, `arcapp_teams`, `arcapp_submittals`,
  `arcapp_workflows`, and `arcapp_item_assignments` (unique constraint changed to
  `(project_key, item_type, item_id)`) all got a `project_key text NOT NULL DEFAULT 'STY4'`
  column — every read filters by it and every write stamps it, so switching to SAN-NT1B starts
  with its own empty Teams/Tasks/Submittals/Settings/Workflows rather than seeing STY4's. Existing
  rows backfilled to `'STY4'` automatically. No new RLS policies were needed — every existing
  policy on these tables already grants access unconditionally (`USING (true)`, or an editor check
  that doesn't reference any column), so project isolation is enforced entirely app-side by the
  `.eq('project_key', ...)`/stamped-column pattern, the same way this app already trusted itself
  (not RLS) for things like a submittal's asset list. `arcapp_authorized_users` (who may sign in
  at all) and `arcapp_workflow_items` (the static catalog of workflow item *types*) were
  deliberately left global — both are app-wide concepts, not per-site data.
- **Two real capability gaps found while wiring up SAN-NT1B** (`hasCapability()` in
  `project.ts`), each showing a clean "not available for this project" notice
  (`CapabilityNotice.tsx`) instead of a broken page, and hidden from the Sidebar entirely:
  - **`siteLogging`** — Tamper Seals and RTFT write to `<prefix>Assets`/`<prefix>RTFT`, and
    SAN-NT1B has neither table yet (confirmed live — 404 from Supabase). Per your call, these
    stay unavailable for SAN-NT1B rather than provisioning matching tables sight-unseen.
  - **`cxAlloyActions`** — Checklists, Issues, the Checklist/Issue To-Do sections, and the CxAlloy
    status pickers in Settings all call custom Apps Script actions (`getChecklists`/`getIssues`/
    `getCxAlloySettings`). SAN-NT1B's separately-deployed script didn't have them yet — confirmed
    live: `action=getChecklists` against it fell through to a different, equipment-tracker-shaped
    default response instead of an error, which would otherwise have rendered as a page of
    blank/malformed rows rather than failing cleanly. **Resolved 2026-09-25**:
    `AppendToCxAlloyScript.gs` was added to SAN-NT1B's own deployment and `cxAlloyActions` flipped
    on for it in `CAPABILITIES`. (Asset Attributes used to share this same capability but was split
    into its own independent Settings toggle the same day — see its own section above; it never
    actually needed the ArcSite-specific actions this capability gates.)
- **What already works for SAN-NT1B**: Activities (`SANNT1BBackEndData`, confirmed live), dropdown
  options, Equipment Status Tracker (reads Supabase directly, not Apps Script — confirmed live with
  837 real assets), Submittals, To-Do (manual tasks/teams), Settings, and — as of 2026-09-25 —
  Checklists/Issues (`cxAlloyActions`, see above). Joint Pack Photos, Asset Attributes, and NETA
  Tracker are all admin-toggleable per project now (see their own sections above) but still need
  their own Sheet/Apps Script deployed for SAN-NT1B before flipping on.
- Verified live end-to-end: switching STY4 → SAN-NT1B updates the site pill and localStorage,
  hides the five gated Sidebar items, shows real SAN-NT1B data on Activities/Equipment Tracker,
  shows the clean unavailable notice on Tamper Seals/Checklists (both direct-URL and Sidebar-
  hidden), and switching back to STY4 restores the full nav and its own data — with zero console
  errors after fixing one component (`CxAlloyStatusPicker`, used by 4 pickers on the Settings
  page) that was still fetching unconditionally regardless of the `cxAlloyActions` gate.
- **RSE1A added 2026-11-02** — same `PROJECTS`/`CAPABILITIES` pattern in `project.ts`, no other code
  changes needed (every table-name template, link-base lookup, and ArcSite-owned table already reads
  `CURRENT_PROJECT`/`CXALLOY_TABLE_PREFIX` generically, same as SAN-NT1B's addition above). Its base
  LaunchPad project (own `launchpad_projects` row, Apps Script deployment, dropdownoptions/
  BackEndData sheet) was confirmed set up, but **both capabilities start off** (`siteLogging: false,
  cxAlloyActions: false`) — neither was confirmed specifically: `siteLogging` needs
  `RSE1AAssets`/`RSE1ARTFT` tables that don't exist for a brand-new project until built, and
  `cxAlloyActions` needs the same custom actions SAN-NT1B's script got
  (`AppendToCxAlloyScript.gs`) also added to RSE1A's own deployment. Flip them on in
  `CAPABILITIES` once each is actually verified — not before, same reasoning as the `cxAlloyActions`
  gap above (an unrecognized action silently returns malformed data instead of erroring). ArcSite's
  own tables need no RSE1A-specific migration either — they're already `project_key`-scoped per the
  bullet above, so switching to RSE1A for the first time just starts with empty Teams/Tasks/
  Submittals/Settings/Milestones, same as SAN-NT1B did.

**⚠️ Unrelated pre-existing security finding, surfaced while checking table constraints for this
migration (not applied — needs your review):** 8 tables in this Supabase project have Row Level
Security **disabled**, fully exposed to the `anon`/`authenticated` keys: `PHXA7_Attributes`,
`SLC1ArcSiteSettings`, `SLC1RTFT`, `STY4ArcSiteSettings`, `STY4RTFT`, `STY4Submittals`,
`user_activity_logs`, `wrappers_fdw_stats`. `STY4RTFT`/`STY4Submittals` were already flagged in the
"Security" section below; `STY4ArcSiteSettings`/`SLC1ArcSiteSettings` are new to me — not tables
this codebase reads or writes (it uses `arcapp_settings`), so they look like leftovers from a
different/earlier ArcSite deployment for STY4 and SLC1. Enabling RLS on any of these without adding
a matching policy first would silently break whatever currently reads them, so review with
whoever owns them before running anything.

## Settings — per-module now, not one long page

As of 2026-10-26, most settings moved out of the single Settings tab (`SettingsPanel.tsx`) and
onto the page they actually configure — a collapsed-by-default **Settings** drawer
(`ModuleSettingsSection.tsx`) near the top of Checklists, Issues, Joint Packs, NETA Tracker, and
Submittals. Visible to everyone (an editor can expand it and see what's configured, same as
before), but every control inside is still admin-only to actually change — same
`Field`/`ToggleField` controls as before (now shared from `SettingsControls.tsx` instead of being
local to `SettingsPanel.tsx`), same "Only admins can change settings." messaging.

**What's still in the Settings tab, and why**: only things that don't belong to one module —
- **CxAlloy project override** — used by both Checklist and Issue deep links, not either one alone.
- **Each module's own enable/disable toggle** (Joint Pack Photos / Asset Attributes / NETA
  Tracker) — has to stay here rather than move to the module's own page, since that page (and its
  Sidebar nav item) doesn't exist to show the toggle on while the module's off. Once a module is
  on, everything *else* about it (script URL, folder ID, To-Do settings) lives on its own page —
  only reachable once the enable toggle up here already let you get there.
- **Workflows** — has no page of its own.
- **Authorized Users** — app-wide access control, not a per-module thing.
- **Sidebar tabs** (added 2026-11-06) — a show/hide toggle for every Sidebar tab except Dashboard
  and Settings themselves: To-Do, Deliverables, Activities, Checklists, Issues, Submittals, Lessons
  Learned, Tamper Seals, RTFT, Equipment Tracker. Unlike the Joint Pack/Asset Attributes/NETA
  toggles above, these default to **visible** when unset (`parseVisible` in `src/lib/api.ts` treats
  anything but an explicit `"false"` as shown) — these are pre-existing tabs every project already
  had, not new modules a project opts into, so leaving the setting key unwritten changes nothing.
  Where a tab is also gated by a `project.ts` capability (Checklists/Issues need `cxAlloyActions`,
  Tamper Seals/RTFT need `siteLogging`), both have to be true — this toggle only narrows further,
  it can't make an unwired capability show up. `Sidebar.tsx` is the only thing that reads these;
  there's no route-level guard behind a hidden tab (unlike Joint Packs' "not wired up yet" page),
  since this is a declutter preference, not a missing-backend error.

Per-page breakdown of what moved where:
- **Checklists page**: Checklist Ready status picker, Checklist To-Do toggle + default assignee.
- **Issues page**: Issues for Review status picker, creator-company filter, Issues To-Do toggle +
  default assignee.
- **Joint Packs page**: Apps Script URL, Drive destination folder ID. The old "no destination set"
  notice used to link to the Settings tab (`onGoToSettings`); now it just expands this same page's
  own Settings drawer in place (`ModuleSettingsSection`'s new controlled `open`/`onOpenChange`
  props, used only here).
- **NETA Tracker page**: Apps Script URL, both To-Do toggles + default assignees (Submissions and
  Returned Files).
- **Submittals page**: exempt-assets manager (`SubmittalExemptAssetsManager`) — this also let
  `SubmittalsManager.tsx` drop its own separate `useGetSettings()` fetch entirely in favor of
  reading `submittalExemptAssets` straight from `ShellContext`, since that was the only field it
  ever used from the full settings object.

## Checklists & Issues (CxAlloy, via Google Sheet)

Unlike the rest of this app, Checklists and Issues don't come from Supabase — they come from the
**"STY4A API Database"** Google Sheet (tabs: `Checklists`, `Issues`, `CxAlloy Settings`), synced
there from CxAlloy by that sheet's own Apps Script. Since this app is 100% client-side and that
sheet is private (not "anyone with the link"), `useGetChecklists`/`useGetIssues` in `src/lib/api.ts`
call the sheet's existing Apps Script **web app** (`doGet`) instead of talking to the sheet
directly:

- The web app's URL is looked up at runtime from `launchpad_projects.google_script_url`
  (Supabase, already `anon`-readable, shared with LaunchPad), keyed by `table_prefix = 'STY4'` —
  not hardcoded, so a redeploy of the Apps Script (same URL) or a different `google_script_url`
  needs no code change here.
- That Apps Script needed three new **read-only, additive** `doGet` actions
  (`getChecklists`, `getIssues`, `getCxAlloySettings`) that didn't exist before this — nothing
  existing in that script was modified. If these ever go missing (script reverted, etc.), both
  panels degrade to the same "couldn't load" error state the rest of the app already uses.
- **Checklist Ready / Issues for Review** (each page's own Settings drawer now, see above) are
  multi-selects populated live from the
  `CxAlloy Settings` tab, not free text. The **Checklist Type** and **Issue Priority** filters on
  the Checklists/Issues pages are *not* sourced from that tab, though — its Type/Priority lists
  don't currently match the names actually used on real rows (e.g. Issue Priority there is
  "P0 - Critical"/etc., but real issues are labeled Low/Moderate/High), so those two filters are
  built from whatever values are actually present in the loaded rows instead. If the CxAlloy
  Settings tab gets reconciled with real data, `ChecklistReadyPanel.tsx`/`IssuesReviewPanel.tsx`
  have a comment marking where to switch that filter's source over.
- Checklist numbers and issue names link out to CxAlloy (`cxAlloyChecklistUrl`/`cxAlloyIssueUrl` in
  `src/lib/api.ts`). The domain+project id those build from — `google.cxalloy.com/70` for STY4,
  `tq.cxalloy.com/49639` for SAN-NT1B — used to be a hardcoded per-project map in
  `src/lib/project.ts`; that meant a code change for every new site, and the STY4 entry (`50506`)
  turned out to be wrong anyway. It's now **auto-detected from this project's own Equipment
  Tracker data** instead (`getCxAlloyLinkBase` in `api.ts`): every `_Link` field that sheet sync
  already produces — `Asset_Link`, `<checklist>_Link`, `<issue>_Link`, etc. — points at the same
  domain+project id, so the first one found (in the first few rows, via PostgREST's jsonb path
  selection — a few KB, not the ~1.6MB full Equipment Tracker payload the tracker page itself
  loads) is enough, confirmed consistent across ~12k real STY4 links and ~2.9k real SAN-NT1B ones.
  A new site's checklist/issue links work with **zero code changes** as soon as its Equipment
  Tracker data syncs — no per-site entry to add anymore.
  - **Settings → CxAlloy project override** shows whatever was auto-detected (so it's visible
    without opening dev tools) and accepts a manual `domain/projectId` override that takes
    precedence — for a brand-new site whose Equipment Tracker data hasn't synced yet, or if
    auto-detection ever finds the wrong thing. Same `arcapp_settings` mechanism as everything else
    there (`cxalloy_link_base_override`), fetched once in `AppShell.tsx` alongside the rest of
    startup state and exposed via `ShellContext.cxAlloyLinkBase` (effective) /
    `cxAlloyLinkBaseDetected` (raw auto-detected value, for the Settings hint).
  - Checklist/Issue rows render as plain text instead of a broken link while `cxAlloyLinkBase` is
    null (still loading, or nothing detected and no override set) — same "degrade gracefully, no
    dead link" approach as everything else CxAlloy-related.
- **Issues — creator company filter** (added 2026-09-25, moved to the Issues page's own Settings
  drawer 2026-10-26): "Issues — creator company filter"
  (`issue_creator_company_filter` in `arcapp_settings`) restricts Issues to ones created by
  a specific company — either the exact string itself (an issue created by a shared/org account,
  where Created By literally *is* the company name) or a person listed under that company in a
  "People" tab (columns `Name`/`Company`, header casing doesn't matter) on the same API Database
  sheet. Applied inside `getIssues`/`getOpenIssues` (`filterByCreatorCompany` in `src/lib/api.ts`),
  so the main Issues page and every To-Do view of issues (summary card count, individually-assigned
  items) agree on the same filtered set. Blank (the default — nothing changes until this is set)
  shows every issue regardless of creator, same as before this existed.
  - The **People tab is synced straight from CxAlloy's own `GET /person?project_id=...` endpoint**
    (paginated the same way `/equipment` already is, via the existing `fetchPaginatedData` helper),
    not hand-maintained — `fetchAndUpdatePeopleData(projectId)` in `AppendPeopleAction.gs` (shared
    separately, not committed to this repo) writes `{first_name} {last_name}` + `company` from each
    record into the tab. Run it the same way the existing `fetchAndUpdateCxAlloySettings` sync is
    already run (it's likewise not called from the main `fetchAndUpdateCxAlloyData()` orchestrator)
    — re-running it just re-syncs from CxAlloy, the tab is never hand-edited.
  - Reading that tab from ArcSite needs one new Apps Script action, `getPeople`, reusing the
    `readFilteredSheet_`/`jsonResponse_` helpers `AppendToCxAlloyScript.gs` already added — see
    `AppendPeopleAction.gs` for the exact one-line addition to `doGet`.
  - **Turning the filter on before `getPeople` is deployed silently shows zero issues instead of
    erroring** — an unrecognized action falls through to a different, equipment-tracker-shaped
    response with no `data` array, which `getPeople()` treats as an empty People list, matching
    nobody. Deploy the script addition first, then set the filter.

## Joint Pack Photos (via Google Sheet + Drive, its own Apps Script)

Same shape as Checklists/Issues, but a **separate** private Google Sheet — **"Joint Pack Photo -
STY4A"** (tabs: `Joint Packs` — Building / Asset / Joint Pack # / Top / Side / Bottom, and
`Settings` — the full "Joint Pack Assets" list) — with its own Apps Script web app, since it's a
different spreadsheet from CxAlloy's. `useGetJointPackData`/`useLogJointPackPhotos` in
`src/lib/api.ts` call it via `doGet`/`doPost`.

- **Diagnosis**: the Joint Packs page cross-references the `Joint Packs` tab's rows against the
  `Settings` tab's asset list to show, per asset, whether it hasn't been started at all, still has
  outstanding sides, or is fully photographed — then drills into a specific asset to show each
  Joint Pack #'s Top/Side/Bottom status individually.
- **Saved photo previews** (added 2026-10-28): expanding a Joint Pack #'s **Log Photos** dropdown
  shows an actual thumbnail (`.jp-saved-thumb`, linking to the full photo on Drive) above each
  side's file picker when a photo's already saved for it, instead of just the collapsed row's small
  "✓" text link — so opening it to check what's already on file (or decide whether it needs
  replacing) doesn't require clicking through to Drive first.
  - The URL stored in the sheet (`DriveApp.getUrl()`'s output, `https://drive.google.com/file/d/
    <id>/view...`) is a viewer *page*, not raw image bytes — it works as a link's `href` (which is
    all this app used it for before the thumbnail existed) but renders as a broken image if used
    directly as an `<img src>`. `driveThumbnailUrl()` in `utils.ts` pulls the file ID out of that
    URL and points the `<img>` at Drive's `thumbnail?id=...` endpoint instead, which does serve
    actual image bytes, while the link itself still goes to the original viewer URL. That endpoint
    still needs the file/folder shared as **Anyone with the link can view** to load without a
    Google sign-in prompt — if thumbnails still show broken after this, check the destination
    folder's sharing setting in Drive before suspecting the code.
- **Photo Gallery view** (added 2026-10-28) — a **View: Asset List / Photo Gallery** toggle above
  the asset search switches away from the original one-asset-at-a-time drill-down to a single
  filterable list of every saved photo across every asset and Joint Pack # at once
  (`JointPackGallery` in `JointPackPhotosPanel.tsx`): one row per asset+Joint Pack #, its asset name
  and Joint Pack # stacked on their own lines to the left, and that pack's saved photos (same Drive
  thumbnail the per-row dropdown shows, each linking to the full photo) laid out to the right —
  rather than repeating the asset/pack label once per photo, which is how this first shipped before
  being reworked the same day into the current grouped-row layout. Filterable by a **Side** toggle
  (All/Top/Side/Bottom — reusing `FilterButtonGroup`, pulled out of `TamperSealLogPanel.tsx` into
  its own file so both can share the same multi-select toggle-button look) and a free-text search
  across asset name + Joint Pack #; a pack with no saved photos left after filtering drops its whole
  row rather than showing one with nothing in it. Only sides that actually have a saved photo appear
  at all — there's nothing to show for an outstanding one. Plain page state, not a persisted
  setting, same as the search box next to it: it's a personal view preference that resets when you
  leave the page, not project configuration.
- **Logging a photo** compresses it client-side (`compressImageFile` in `utils.ts` — downscaled to
  1600px, JPEG ~0.82 quality, to keep uploads fast on-site) then POSTs it to the Apps Script, which
  uploads it to Drive (via `DriveApp`, running as the script's own account — no per-user Google
  Drive permission needed) into the folder ID set in the **Joint Packs page's own Settings
  drawer**, named
  `Building - Asset - Joint Pack # - Side.jpg`, and writes that file's URL back into the matching
  Top/Side/Bottom cell. Logging a photo for a Building/Asset/Joint Pack # combination that isn't in
  the sheet yet appends a new row for it — the app doesn't require pre-registering a Joint Pack #
  before photographing it.
- **Per-project on/off toggle + editable URL** (added 2026-09-25 while onboarding
  SAN-NT1B — this used to be shown unconditionally for every project, with the URL DB-only). The
  main **Settings tab**'s "Joint Pack Photos enabled for this project"
  (`joint_pack_enabled` in `arcapp_settings`/`jointPackEnabled` in `AppSettings`) gates the page and
  its Sidebar nav item (`CapabilityNotice` when off, same pattern as NETA Tracker/siteLogging/
  cxAlloyActions), same reasoning as NETA Tracker's toggle: a newly-onboarded project shouldn't
  show a page that just errors before its own Sheet/script exists — that's why this one toggle
  stays in the main Settings tab instead of moving to the Joint Packs page with everything else
  (2026-10-26), since the page doesn't exist to show it on while it's off. The Apps Script's URL
  itself (`joint_pack_script_url`) is an editable Field on the **Joint Packs page's own Settings
  drawer** instead of DB-only — an admin can wire up a new project's deployment themselves. STY4
  was seeded with the toggle on to preserve its existing behavior; SAN-NT1B starts off.
  Redeploying the script as a new version of the same deployment keeps the same URL; only a
  brand-new deployment needs this field updated.
- The script itself (`doGet`/`doPost`, not committed to this repo — see `JointPackPhotoScript.gs`
  shared separately, same as CxAlloy's script isn't committed here either) needs to be pasted into
  **Extensions → Apps Script** on the "Joint Pack Photo - STY4A" spreadsheet and deployed as a web
  app (**Execute as: Me**, **Who has access: Anyone**) — its Drive permission is whatever Google
  account owns that deployment, so that account needs write access to the destination folder.
- **In-page camera** (`JointPackCameraWorkspace` in `JointPackPhotosPanel.tsx`, opened via **Open
  Camera** in the page header, not nested under any one asset): a live `getUserMedia` feed (rear
  camera preferred via `facingMode: environment`) alongside two picker columns — **Asset**, then
  **Joint Pack #** — with Top/Side/Bottom angle tabs above the feed itself. The camera stream is
  requested once when this opens and stays live for as long as it's open; switching asset, Joint
  Pack #, or angle only changes where the next shutter press gets filed; none of it stops or
  re-requests the camera, so a crew walking a row of assets never has to "click in and out" between
  shots. Each shot is drawn to a canvas and compressed the same way as a picked file (1600px/0.82
  JPEG) and queued (with a thumbnail on its angle tab and a status dot on its Joint Pack # in the
  column); **Save Photos** uploads whatever's queued for the currently-selected Joint Pack # only —
  switching away and back preserves anything queued elsewhere that hasn't been saved yet. A new
  Joint Pack # can be typed directly into the second column without leaving camera mode. Per-row
  `<input type=file>` fields still exist as a fallback (e.g. picking an existing photo from the
  library, or browsers without camera support) — expand a row's **Log Photos** to use those instead.
  Requires a secure context (HTTPS or localhost) and camera permission — Chrome/Safari will prompt.
  (`FullscreenOverlay` — used by this and other full-screen panels — portals its content directly
  onto the `.arcapp` root rather than rendering in place, because `<main>` has its own
  `position:relative; z-index:1` that would otherwise trap a z-index:100 overlay mounted from deep
  inside it, rendering it behind the sidebar wherever the two overlap on screen.)
- Logging photos doesn't require signing in (same as Tamper Seal/RTFT logging) — only changing the
  destination folder in Settings is editor-gated.

## NETA Tracker (mirrors a live Google Sheet, two-way — via its own Apps Script)

`NetaTrackerPanel.tsx` reproduces the **"STY4 NETA Tracker"** spreadsheet's `Submissions` and
`Returned Files` tabs inside ArcSite — same Zone → Area → Asset Category grouping, same checkboxes,
same Comments field — and unlike every other Sheet-backed feature in this app, **writes back to
it**: toggling a checkbox or editing a comment here sets that exact cell in the live sheet the
field crew already works from, so ArcSite never becomes a second, drifting copy of the tracker. A
third private spreadsheet, a third dedicated Apps Script (separate from both CxAlloy's and Joint
Pack Photo's) — `useGetNetaTrackerData`/`useUpdateNetaField` in `src/lib/api.ts` call it via
`doGet`/`doPost`, same shape as the other two.

- **Row hierarchy**: the sheet doesn't use native Sheets row grouping — instead it has special
  single-cell marker rows above each section: `ZONE HEADER: ZONE 1`, `------ AREA: EY09 ------`,
  `[ ASSET CATEGORY: ATX-A ]`. The script walks each tab top to bottom, matches these three
  patterns, and stamps every data row below with the nearest zone/area/category above it, so
  `api.ts` never needs to know that convention — it just gets `{ zone, area, category }` on every
  row. (Found by downloading the actual workbook and inspecting tab names/headers directly — the
  natural-language sheet read tool only ever surfaces one tab, and this spreadsheet has seven:
  `UGLY`, `Submissions`, `Returned Files`, `Submission Tracker`, `BlEH`, `SUBMISSIONS -`,
  `RETURNED FROM GOOGLE` — only the two the user asked for are wired up.)
- **Columns**:
  - `Submissions` — Document Name, Submitted Date, Folder Location, Document Link (all read-only
    display), then editable **Clerical Review**, **Submitted to Google**, **Issues Found**
    (checkboxes) and **Comments** (text).
  - `Returned Files` — same four display columns, then **Issues** (free text, shown as a caution
    chip when it isn't blank/"None"), editable **Technical Review**, **Stamp Present**, **Neta
    Completed**, **Uploaded to ACC** (checkboxes) and **Comments**.
  - `DOCUMENT NAME` and the `FOLDER LOCATION` pill are both clickable, opening the same place a
    click in the sheet would — the actual Drive file and its Drive folder respectively. Both sheet
    cells are `=HYPERLINK(url, "label")` formulas (not native cell links, and not visible via
    `getValues()`), so `readNetaTab` in the script also reads `getFormulas()` for those two columns
    and regexes the URL out, returned as `documentLinkUrl`/`folderLocationUrl` alongside each row.
    A row falls back to plain, non-clickable text for either one if its cell somehow isn't a
    HYPERLINK formula (never observed in practice — 778/778 and 119/119 had one when checked).
- **Writes are addressed by literal sheet row number** (returned alongside each row by
  `getNetaData`), which is fast but fragile if rows get inserted/deleted between page load and an
  edit — `updateNetaField` also sends the row's `documentName`, and the script refuses the write
  (with a clear error) if column A of that row no longer matches, rather than silently editing the
  wrong row.
- **"Show completed"** (off by default) hides rows already at their terminal checkbox —
  `submittedToGoogle` for Submissions (the sheet's own header note says that checkbox hides the row
  there too), `uploadedToAcc` for Returned Files — mirroring how the sheet is normally worked from.
  Search matches document name/area/category and auto-expands the whole tree while active.
- The Apps Script's URL is stored in `arcapp_settings` under `neta_tracker_script_url` — set
  directly in Supabase, same as `joint_pack_script_url`; not an editable Settings field. Reading it
  requires the `arcapp_settings` SELECT policy to allow `anon` too, not just `authenticated` — a
  pre-existing gap (found while wiring this up) that also silently broke Joint Pack Photos and a
  few other features for signed-out users; fixed the same day this was found.
- **`NetaTrackerScript.gs` is this spreadsheet's one bound script, not an ArcSite-only file** — it's
  a merge of two independent pieces that happen to share the same project:
  1. The **existing Drive-folder importer + checkbox automation** that was already there (a
     "Document Importer" menu that crawls Drive and rebuilds both tabs' grids, plus an installable
     `onEdit` trigger — `masterTrigger` → `onCheckboxEdit`/`onReturnedFilesEdit` — that moves a
     file between Drive folders and applies the Submissions red-issue highlight when a checkbox is
     toggled by a person in the sheet UI).
  2. **ArcSite's web app** (`doGet`/`doPost`).

  These have to live in the same Apps Script project because Google Sheets' `onEdit` triggers
  (simple or installable) **only fire for edits made through the Sheets UI by a person** — never
  for edits made programmatically via `Range.setValue()`, whether that call comes from this same
  script or a different one. Without doing anything about it, a checkbox toggled from ArcSite would
  silently skip the Drive-move/highlight automation entirely. Fix: `updateNetaField` calls
  `onCheckboxEdit`/`onReturnedFilesEdit` itself, right after `setValue()`, passing a minimal
  `{ range }` object — the only piece of the real event object either function actually reads — so
  an ArcSite edit runs the identical follow-on automation a real click would. A failure in that
  automation (e.g. a Drive move erroring) never fails the write itself; the cell is already
  correctly set by that point, same as a real `onEdit` trigger throwing wouldn't undo the checkbox.
- **Stamp Present / Uploaded to ACC can be "N/A", not just checked/unchecked**: the importer leaves
  those two Returned Files cells as the literal text "N/A" (no checkbox at all) while a row's
  Issues column isn't "None" — they can't be resolved until the issue is cleared. `getNetaData`
  passes that string through untouched (no boolean coercion in the script), `netaBoolOrNA` in
  `api.ts` tells "N/A" apart from a real boolean, and `NetaCheckboxOrNA` in the panel renders a
  fixed, non-interactive "N/A" tag instead of a checkbox for either field on those rows —
  `updateNetaField` also refuses the write server-side if the row's Issues column isn't "None",
  so nothing (ArcSite UI, a stray API call) can silently overwrite that marker with `true`/`false`.
  (Found and fixed a related bug live: the "Show completed" filter's `r.uploadedToAcc` truthiness
  check treated the *string* `"N/A"` as truthy, hiding open-issue rows behind that toggle by
  mistake — changed to `r.uploadedToAcc === true`.)
- **Gated by a per-project Settings toggle, not a project.ts capability** (changed 2026-09-25 —
  `netaTracker` used to be a third hardcoded capability alongside `siteLogging`/`cxAlloyActions`,
  requiring a code change/redeploy to turn on for a new site). The main **Settings tab**'s "NETA
  Tracker enabled for this project" (`neta_tracker_enabled` in `arcapp_settings`,
  `netaTrackerEnabled` in `AppSettings`/`ShellContext`) is admin-toggleable per project — flip it on
  once that project's own NETA Sheet + Apps Script are actually deployed, no ArcSite code change
  needed. Off shows the standard "not available for this project" notice, same as before; the
  toggle itself always renders (even while off) so an admin can find and flip it — same reasoning
  as Joint Pack Photos' toggle for why this one stays in the main Settings tab rather than moving
  to the NETA Tracker page with everything else (2026-10-26). STY4 was seeded with this on
  (`neta_tracker_enabled = 'true'`) to preserve its existing behavior across the change; SAN-NT1B
  starts off, same as before. Its Apps Script URL (`neta_tracker_script_url`) is an editable Field
  on the **NETA Tracker page's own Settings drawer** (used to be DB-only, then briefly lived in the
  main Settings tab) — same reasoning as Joint Pack Photos' URL field.
- No sign-in required to toggle checkboxes or edit comments, same as Tamper Seal/RTFT logging.
- **Verified against the real deployed script and real sheet data** (778 Submissions / 119 Returned
  Files rows): `getNetaData`'s shape and row counts match a direct workbook inspection exactly; a
  real write applies and is visible on the next read; the row-shift guard correctly refuses a
  write when `expectedDocumentName` doesn't match; the field whitelist correctly refuses writing to
  a non-editable column; a test write was reverted afterward, leaving the sheet exactly as found.
  Hyperlinks (Document Name → Drive file, Folder Location → Drive folder), tree expand/collapse,
  search, tab switching, "Show completed", the N/A-vs-checkbox rendering, and the SAN-NT1B
  capability gate were all confirmed via Playwright against a mocked response (matching the real
  script's shape) — zero console errors throughout.

The Tamper Seals page (`TamperSealLogPanel.tsx`) used to be read-only — seals could only be logged
from inside an Activity's drawer. **Log Seals** in its header now opens the exact same range-entry

- **Asset dropdown + auto-filled Place**: `getAssetPlaceOptions()` in `src/lib/api.ts` reads

  changes the actual selected asset (so Place/Confirm stay tied to the last real pick), and

- **Signoff**: already automatic and unrelated to this change — `logTamperSeals()` stamps
  `signoff` from the signed-in session's email server-side on every insert (activity-drawer or
  standalone), and the form's hint line under Generate Preview shows "Signed in as X" (or "not
  signed in") so it's clear before submitting either way.
- `TamperSealSection` itself was generalized to take a plain `assetName`/`location` pair instead
  of requiring a whole `ScheduleRow` — the Activity Drawer usage just passes
  `activeRow.asset`/`activeRow.place` now.
- **Filtering** (added 2026-10-26, ported from LaunchPad's own Tamper Seal log) — a filter bar
  above the table: multi-select **Location** and **Status** toggle-button groups (both default to
  "All"; clicking a specific value drops "All" and toggles that value, clicking "All" clears back
  to just "All", emptying the set falls back to "All" rather than matching nothing —
  `toggleFilterValue`, now in its own `FilterButtonGroup.tsx` — moved out of this file 2026-10-28
  so Joint Pack Photos' gallery filters could reuse it too) plus a free-text **search** across asset/
  location/seal #/sub area/notes/signoff. Deliberately multi-select toggle buttons rather than the
  single-select dropdowns Checklists/Issues/Submittals use elsewhere in this app — that's
  LaunchPad's own UX for this specific page, matched as asked rather than homogenized to ArcSite's
  usual pattern. Location/Status option lists are derived from whatever's actually in the loaded
  rows (same technique the Checklist Type/Issue Priority filters already use), not a separate
  admin-configured status catalog the way LaunchPad's `getActiveStatuses()` works — ArcSite has no
  such catalog for Tamper Seals. LaunchPad's more elaborate match-navigation (highlight + prev/next
  + counter) and PDF/CSV export weren't ported — out of scope for what was asked.
- **Break request approval** (added 2026-10-26) — LaunchPad's field form (`seal-form-view.js`,
  `submitBreakRequest`) lets a worker request to break a seal: it flips that seal's `STY4Assets`
  row to status `Break Requested (Pending Approval)` and best-effort logs the requestor's name/
  company/email/reason into `STY4BreakRequests` (plus a per-seal row into `STY4RequestedSeals`).
  Nothing in LaunchPad itself ever reads the `ccm_decision` field back, though — there was no
  approval UI anywhere, for either app. ArcSite is now that missing half:
  - A worker can select several seals in one submission (LaunchPad's form logs this as a single
    `STY4BreakRequests` row with a comma-joined `requested_seal_numbers`, not one row per seal), so
    `TamperSealLogPanel.tsx` groups pending seals back into their original batch before showing
    them — a **Pending Break Requests** card per batch, above the filter bar, listing the
    requestor's name/company/email/reason once and every seal in that submission underneath
    (`getBreakRequests` in `src/lib/api.ts` does the asset-name + seal-number matching). Any
    signed-in authorized user (`canEdit`, editor or admin) gets an **Approve**/**Deny** toggle per
    seal — a batch of 6 can be any mix, e.g. 4 approved and 2 denied — then **Submit decisions**
    applies them (`useDecideBreakRequests`); approving a seal sets it
    to `Break Approved by CCM` (continuing LaunchPad's existing workflow), denying reverts it to
    `Intact` — matching the progression already shown in LaunchPad's own Tamper Seal log settings
    (accept moves forward a stage, deny sends it back to Intact rather than a dead-end status). The
    batch's `STY4BreakRequests.ccm_decision` is re-derived from every seal's current status after
    each decision (not just the ones just acted on) — `Pending` while any seal in the batch is
    still awaiting a decision, `Approved`/`Denied` once they're unanimous, `Partially Approved`
    for a mixed outcome.
  - `STY4BreakRequests` and `STY4RequestedSeals` **did not actually exist** in the live database
    before this — LaunchPad's insert into them was silently failing (RLS/`PGRST205`). They've been
    created now (open RLS, matching `STY4Assets`'s `anon, authenticated` policy, since Tamper Seal
    logging is "no sign-in required" throughout), plus `decided_by`/`decided_at`/`decision_notes`
    columns on `STY4BreakRequests` for the approval step itself. Because those tables didn't exist
    yet, the handful of break requests already pending in production before this change have no
    requestor name/company/reason on file — those rows show "No request details on file" instead.
  - The live `launchpad_tamperseal_config` workflow (`project_key='STY4'`) was updated to add a
    `break_requested → intact` transition (`t2b`), since the deny path didn't exist in the
    workflow graph at all before this.
  - **Review flow (ARC-323, 2026-11-10)** — **Submit decisions** stays disabled until every seal
    in the batch is set to Approve or Deny (the hint shows "N of M done"), so a batch is always
    decided in one go. Denying a seal opens a short note field for why, and each card has a
    **General notes** box. Both are saved to `STY4BreakRequests.decision_notes` (general notes,
    then one `Seal #… denied: …` line per denial note; a later round appends instead of
    overwriting), so no schema change was needed.
  - **Decision email** — after the decisions save, the requestor is emailed the outcome: overall
    decision, each seal Approved/Denied, reviewer, and the notes. It goes through the
    `seal-decision-email` Edge Function (`sendBreakDecisionEmail` in `src/lib/api.ts`), which
    builds the email server-side from the `BreakRequests` row and the seals' current statuses and
    always sends to that row's `requestor_email`, so the browser can't pick the recipient or the
    content. Reply-To is the reviewer. Batches with no request row (the legacy orphans) or no
    requestor email aren't emailed. A failed or unconfigured email never undoes the decisions;
    the panel says "Saved" and shows why the email wasn't sent.
  - **Sender: arclab@criticalarccx.com.** The Edge Function hands the finished email to a small
    Apps Script web app (`apps-script/arclab-mailer/Code.gs`) that's deployed by the arclab@
    account, so Gmail sends it as arclab@. The script only sends when the request carries a shared
    secret, and it refuses to run if it was deployed from any other account. Setup, once:
    1. Signed in to Google as arclab@criticalarccx.com, create a project at script.google.com and
       paste in `Code.gs`.
    2. Project Settings → Script properties → add `MAILER_SECRET` with a long random value.
    3. Deploy → New deployment → Web app, **Execute as: Me**, **Who has access: Anyone**, and
       authorize the Gmail permission. Copy the `/exec` URL.
    4. Deploy the function and set its secrets:
       ```
       supabase functions deploy seal-decision-email
       supabase secrets set ARCLAB_MAILER_URL=<the /exec URL> ARCLAB_MAILER_SECRET=<same value as step 2>
       ```
    Gmail's Workspace limit is about 1,500 recipients a day for the account, far above what
    break requests need.

## Submittals — one record per document, applied to many assets

Reworked from the ground up. The old model (`STY4Submittals`) was one row **per asset** — every
asset had its own independent review status/notes, with no way to represent "this one document
covers 12 assets" other than repeating the same review by hand 12 times. The new model
(`SubmittalsManager.tsx`, backed by a new `arcapp_submittals` table) flips that: a submittal is its
own record — a title, an uploaded file, and a `assets` array — and setting its review status/notes
once applies to every asset in that array simultaneously, because they all point at the same row.
There's no propagation logic to get right; it's just what "one row, many assets" already means.

- **Uploading a file**: `useUploadSubmittalFile()` sends it straight to Supabase Storage (a new
  public `submittals` bucket, created alongside the table), which is the one part of this that
  needed net-new infrastructure — everything else in the app either reads Google Sheets (CxAlloy,
  Joint Pack Photos) or writes to Postgres directly. The bucket is public for reads (so a
  submittal's file link works for anyone with it) but writes are editor-gated, same as the table.
- **Picking assets**: `MultiSelectPicker.tsx` — a search box + checkbox list + removable chips +
  `Select all`/`Select all shown`/`Deselect all`, extracted from the picker `WorkflowsBuilder`
  already had for linking Activities to a Workflow (same interaction: pick a subset of a long
  list). Also used by the new exempt-assets picker in Settings (below).
- **Status**: every submittal starts at **Not Started** (`SUBMITTAL_STATUSES` in `src/lib/api.ts`
  — there's no blank/unset state anymore) and can be changed two ways: from the create/edit form,
  or inline right on its card (a small `<select>` next to the title that saves immediately on
  change) — both editor-gated. **Filter by status** above the list narrows to one status at a time.
- **Notes are an append-only log, not a single field**: the old `notes` text column (one
  overwritable string) is retired in favor of `notes_log` (jsonb array of `{text, author, at}`,
  never touched by the general edit-submittal save). Each card has a **Notes (N)** dropdown —
  opening it shows the full history newest-first with who left each note and when, plus an
  **Add Note** box at the top for editors. `notes` itself is left in the table, unused (there was
  nothing in it worth migrating).
- **Missing-submittal count**: the header badge is every tracked asset (`STY4dropdownoptions.
  Assets`) that isn't covered by any submittal's `assets` array — hover it to see which ones.
  The Submittals page's own Settings drawer → **Assets Exempt From Submittal Review**
  (`SubmittalExemptAssetsManager.tsx`, moved here from the main Settings tab 2026-10-26; a
  `submittal_exempt_assets` setting) lets you mark assets that will never need one (e.g. nothing
  commissionable in that space) so they're excluded from the count entirely, rather than sitting
  there permanently flagged as "missing." An **Exempt Assets** button next to **New Submittal** in
  the header (added 2026-10-27) jumps straight to that drawer instead of needing to find/expand the
  page's own collapsed-by-default Settings toggle first — same controlled-open pattern Joint Packs'
  "no destination folder set" notice already used to jump to its own Settings section.
- **Export**: the button next to the status filter zips every *currently filtered* submittal's
  file (client-side, via `jszip` — fetches each file, bundles them, triggers one download named
  `submittals-<status>-<date>.zip`) so you can pull, say, every Approved submittal's paperwork in
  one go. Submittals with no file attached are skipped; if none of the filtered ones have a file,
  it tells you that instead of downloading an empty zip.
- **RLS**: viewable without signing in (`submittals_select_public`, matching Checklists/Issues/
  Joint Pack Photos — status is useful to anyone on-site), but creating/editing/deleting a
  submittal (and uploading/replacing/removing its file in Storage) requires being an authorized
  editor — this was already true client-side via the old panel's `canEdit` gate, now it's also
  enforced by real RLS policies instead of trusting the UI alone.
- `STY4Submittals` itself is untouched and still exists in the database — nothing currently reads
  it, so it's safe to leave alone (or drop later) unless something else depends on it.

⚠️ **Known issue surfaced while building this, not yet fixed**: `arcapp_settings`' SELECT policy
is `TO authenticated` only — **anonymous (not-signed-in) users currently can't read settings at
all**, silently getting empty defaults back instead of an error. This isn't specific to
Submittals — it equally affects Joint Pack Photos' Drive-folder/script-URL lookup and the
Checklists/Issues ready-status filters for anyone not signed in, since they all read through the
same `getSettings()`. The fix is a one-line policy swap (`settings_select_authenticated` →
`TO anon, authenticated`, matching every other "viewable without signing in" table in this file),
but changing a live RLS policy needs your explicit go-ahead rather than being applied
automatically — ask for it to be applied when you're ready.

## Google Chat bot — notifications + slash commands

**Added 2026-11-05.** Two small Supabase Edge Functions connect ArcSite to a Google Chat space,
scoped to one project for now:

- **`chat-notify`** (outbound) — ArcSite posts a message into the space whenever a **critical
  to-do** is added or a **new lesson learned** is logged (`notifyGoogleChat` in `src/lib/api.ts`,
  called from `saveTask`/`saveLessonLearned` on create only, best-effort — a Chat failure never
  blocks the underlying save). Settings also has a "Send test message" button that goes through
  the same function.
- **`chat-bot`** (inbound) — an interactive bot you can `@mention` or DM in the space. It
  understands three commands, typed with or without the leading `/`:
  - `/status` — open to-do count, overdue deliverable count, total lessons learned logged
  - `/todo <text>` — adds a to-do (tagged "norm"), attributed to the Chat sender's display name
  - `/lesson <text>` — logs a lesson learned (category "Other"), same attribution

Both functions live in `supabase/functions/` and read/write the same tables the app does
(`arcapp_tasks`, `arcapp_lessons_learned`, `arcapp_milestones`, `arcapp_settings`) via the service
role key, which Supabase injects into every Edge Function automatically — no new secret needed for
that part.

### Setting up outbound notifications (the easy half)

1. In the target Google Chat space: **Apps & integrations → Webhooks → Add webhook**, name it
   "ArcSite", and copy the URL it gives you.
2. In ArcSite: **Settings → Google Chat webhook URL** (admin-only field), paste it in, Save.
3. Click **Send test message** right below it to confirm it posted.

No Edge Function deployment is required for this half if you're doing it on a Supabase project
that already has `chat-notify` deployed (see below) — if notifications are the only thing you want,
you still need to deploy `chat-notify` once (it's what the webhook URL and the app's own writes
actually go through), but you can skip the Google Cloud Console steps below entirely.

### Setting up the interactive bot (the involved half)

This part needs an actual Google Chat app, which means a Google Cloud project — there's no way
around that for a two-way bot, and it's a one-time setup per Workspace:

1. **Google Cloud Console** → create or pick a project → enable the **Google Chat API**.
2. **Google Chat API → Configuration**: give it a name/avatar/description, under
   **Interactivity** choose "App can be messaged via HTTP" / "App URL" and set the endpoint (see
   step 4 below for the exact URL), turn on **Receive 1:1 messages** if you want DMs, and set
   **Visibility** to whoever in your Workspace should be able to add it (or "anyone" for personal
   testing).
3. Deploy the two functions to your Supabase project (the Supabase CLI isn't linked in this repo's
   dev environment, so this always has to be run from somewhere that's logged in):
   ```
   supabase login
   supabase link --project-ref <your-project-ref>
   supabase functions deploy chat-notify
   supabase functions deploy chat-bot --no-verify-jwt
   ```
   `chat-bot` needs `--no-verify-jwt` because Google Chat doesn't send a Supabase-issued session
   token — it's verified with its own shared secret instead (next step), not Supabase's gateway.
4. Set that shared secret, and which project this bot instance is for, as function secrets:
   ```
   supabase secrets set CHAT_SHARED_SECRET=<a long random string you make up> ARCAPP_CHAT_DEFAULT_PROJECT=STY4
   ```
5. Back in Cloud Console, set the HTTP endpoint from step 2 to:
   ```
   https://<your-project-ref>.supabase.co/functions/v1/chat-bot?token=<the CHAT_SHARED_SECRET value>
   ```
   Treat that full URL as a secret — anyone who has it can post to this function as if they were
   Google Chat. (`?project=<KEY>` can be added to the URL instead of relying on
   `ARCAPP_CHAT_DEFAULT_PROJECT`, which is how a second project would get its own bot/space later:
   a second Chat app in Cloud Console pointing at this same function with a different `project`
   value — no code change needed.)
6. Set the app's status to **Live** and add/publish it to the space you want it in, then
   `@ArcSite /status` to confirm it responds.

## Load speed — shared requests (ARC-321)

Several parts of the app load the same data on their own. On the Dashboard, the Milestones widget
and the shell's Checklist/Issue/NETA to-do loader each fetched the same CxAlloy checklists,
issues, status vocabulary, people list and NETA data, and each of those first re-read the project
settings and the Apps Script URL. A first Dashboard load with every module on made roughly 19 Apps
Script calls and 30 small Supabase reads, where about 8 and 2 are needed. Apps Script queues calls to
one deployment, so the duplicates made every call slower.

`src/lib/requestCache.ts` (`shareRequest`) now gives every caller the same request while it's in
flight and keeps the result briefly afterwards:

| Data | Shared for | Cleared by |
| --- | --- | --- |
| Project settings (`arcapp_settings`) | 60 s | any `saveSetting` (Settings saves, default assignees) |
| CxAlloy Apps Script URL | 5 min | page reload / project switch |
| CxAlloy sheet reads (checklists, issues, statuses, people) | 15 s | n/a (read-only actions) |
| NETA Tracker data | 15 s | any `updateNetaField` |
| Joint Pack data | 15 s | any `logJointPackPhotos` |

A failed request is never kept, so the next try goes out fresh. A Refresh click within 15 s of the
last load can return that same data, which is the trade-off for sharing it.

`jszip` is now loaded only when a Submittals zip is downloaded, which takes ~97 kB (30 kB gzipped)
off every page load.

**Not done yet** (bigger, needs LaunchPad's sync): having the CxAlloy checklists/issues already in a
Supabase table, the way the Equipment Status Tracker's data is synced by a GitHub Action, so the
Dashboard never waits on Apps Script at all.

`KpiRow.tsx` was still the original Retool-era mock — all four tiles (Milestones GO, Open to-dos,
Systems in commissioning, Next milestone) were hardcoded literals, never wired up even after the
features they describe became real. Fixed 2026-10-29, same inputs `DashboardPage.tsx` already had
on hand for its other widgets — no new fetches:

- **Deliverables GO** (tile label changed 2026-11-02 — see "Milestones → Deliverables" below;
  everything underneath still reads from the `Milestone`/`milestones` types and tables, unchanged):
  `{count with progress.status === 'go'} / {total milestones}`, from the same
  `useMilestonesWithProgress` call `MilestonesPanel`'s widget uses — never disagrees with the
  Deliverables page. Sub-line counts Caution/Hold milestones as "need attention" (red dot if any
  are Hold, amber if only Caution, green "All on track"/"All complete" otherwise).
- **Open to-dos**: `todos.filter(t => !t.done).length + extraOpenCount` — the exact same formula
  `TodoPanel.tsx`'s own header count uses, given the exact same `myTodos`/`extraOpenCount` props, so
  this tile can't drift from what "Your To-Dos" shows. Sub-line counts how many are due today (or
  overdue — `todoDueDisplay().today` covers both) via the existing `todoDueDisplay` helper.
- **Scheduled Activities** (renamed from "Systems in commissioning", which never meant anything
  concrete here) — a plain count of `ctx.rows`, the same Schedule rows `SchedulePanel` below it is
  already showing for whichever day is selected. Sub-line counts distinct `trade` values among them
  ("3 disciplines active" / "Nothing scheduled").
- **Next deliverable**: the soonest `dueDate` among milestones not yet at `complete` status,
  sourced from that same `useMilestonesWithProgress` list — "T−NND" countdown, "Today", or "NND
  late" once past due, with the deliverable's name underneath. Red sub-line once due or overdue,
  amber inside 3 days, otherwise neutral; "No upcoming deliverables" when none have a due date or
  all are complete.

## Milestones → Deliverables — criteria-driven progress, not hand-set

**Nomenclature note (2026-11-02):** this module's user-facing name changed from "Milestones" to
"Deliverables" — the Sidebar nav item, page heading, button labels, and KPI tiles all say
"Deliverable(s)" now. Nothing underneath was renamed: the TypeScript type is still `Milestone`, the
table is still `arcapp_milestones`, the page file is still `MilestonesPage.tsx`, settings keys are
still `milestone_*`, and so on — this was a surface-level rename of what people read, not the data
model, to keep the change small and low-risk. The rest of this section (and the one above) still
say "milestone" throughout for exactly that reason — read it as "deliverable" wherever it appears.

Used to be entirely fake: `sampleData.ts` hardcoded six milestones with a hand-picked pct/status,
rendered read-only on the Dashboard and the Milestones page (now deleted — nothing reads it
anymore). The Milestones page (`MilestonesPage.tsx`) is now fully editable, backed by a new
`arcapp_milestones` table (`project_key`-scoped, same pattern as Submittals/Tasks/Teams), and a
milestone's pct/status are **computed live, every page load**, from a list of completion criteria
instead of being set by hand.

- **A criterion** scopes into one other module — Checklists, Issues, or Submittals by either an
  explicit asset list **or by area** (added 2026-10-27), + which status(es) on that module count as
  "done"; NETA Tracker by a tab (Submissions/Returned Files) + zone(s) + which boolean field
  (Clerical Review, Technical Review, NETA Completed, etc.) counts as done; or Joint Pack Photos
  (added 2026-10-30) by asset/area only — it has no status vocabulary, so a Joint Pack # row just
  counts as done once all three sides (Top/Side/Bottom) are photographed. Gated by that project's
  `jointPackEnabled` toggle the same way NETA criteria are gated by `netaTrackerEnabled` — the
  module option doesn't even show up in the picker if Joint Pack Photos isn't turned on.
  `MilestoneCriteriaBuilder.tsx` is the editable list of these inside the Add/Edit Milestone form;
  `evaluateCriterion`/`computeMilestoneProgress` (`src/pages/arcapp/milestones.ts`) are the pure
  functions that turn `criteria` + each module's current data into a result — **nothing is stored
  except `criteria` itself**, so there's no stale pct sitting in the database disagreeing with
  reality.
  - **Scope by area**: a Checklists/Issues/Submittals criterion's "Scope by" toggle switches
    between **Asset** (pick specific assets) and **Area** (pick one or more Places — same
    Asset↔Place pairing from `STY4dropdownoptions` that Tamper Seal/RTFT already use to auto-fill
    Place from Asset). An area-scoped criterion resolves to "every asset currently paired with one
    of these Places" at evaluation time (`resolveScopeAssets` in `milestones.ts`), not a frozen
    snapshot — an asset added to that area later is automatically picked up without editing the
    criterion. `CriterionScope` (`{ by: 'assets', assets }` or `{ by: 'areas', areas }`,
    `src/lib/api.ts`) replaced the old flat `assets: string[]` field; `parseMilestoneCriteria` still
    reads the old shape from any criterion saved before this change.
  - **Issues criteria can also filter by priority** (added 2026-10-27) — an optional multi-select
    (none selected = every priority counts) on top of the asset/area scope and target status, so a
    criterion can track e.g. only Critical-priority issues for an area instead of every issue
    regardless of severity. `IssueCriterion` is its own type now (`priorities: string[]`, distinct
    from `ChecklistCriterion`, which has no priority concept) — `parseMilestoneCriteria` defaults
    `priorities` to `[]` for any Issues criterion saved before this field existed.
- **Combining criteria**: a milestone's overall pct is the plain average of each criterion's own
  pct (not weighted by how many items each one covers) — by request, so a milestone rests on
  several conditions clearing roughly together rather than needing every last one done before
  showing any progress. A criterion with zero matching items (nothing picked yet, or the picked
  assets/zone have no rows in that module) is left out of the average entirely rather than counted
  as 0% or 100% — a misconfigured criterion shouldn't silently look either done or stuck.
- **Status thresholds are configurable** (added 2026-10-28), not fixed — the Milestones page has its
  own **Milestone Statuses** button/Settings drawer (admin-only like every other per-module
  Settings control), split into two pieces:
  - `MilestoneStatusThresholdsManager.tsx` — three pct inputs: Complete, Go, and Caution (anything
    below Caution is Hold). Checked in that order — `statusForPct` in
    `src/pages/arcapp/milestones.ts` — so pct ≥ Complete wins first, then ≥ Go, then ≥ Caution, else
    Hold; keeping them in descending order (Complete ≥ Go ≥ Caution) is on the admin, same as the
    in-app hint says. Stored as three `arcapp_settings` rows (`milestone_complete_threshold`/
    `milestone_go_threshold`/`milestone_caution_threshold`), defaulting to 100/70/40 — the fixed
    values this app shipped with before they were editable.
  - `MilestoneStatusStylesManager.tsx` (added 2026-10-28) — what each of the four buckets is
    actually called and colored (a text label + a native color picker per bucket, e.g. relabel
    "Hold" to "Blocked" or pick project-specific colors), separate from which bucket a milestone
    falls into — that's still decided by the thresholds above. Stored as one JSON-encoded
    `arcapp_settings` row (`milestone_status_styles`, parsed/validated by
    `parseMilestoneStatusStyles` in `src/lib/api.ts`, falling back to the default label/color per
    bucket on anything malformed) rather than eight separate keys. `computeMilestoneProgress` now
    returns a `color` alongside `label`, and both the Milestones page and the Dashboard widget
    render the status chip/progress ring from that color via inline style instead of the old fixed
    CSS modifier classes (`status-chip.go`/`.caution`/etc.), which only ever supported the built-in
    palette.
- **Checklists/Issues criteria see every status, not just "Ready"/"for review"**: `useGetChecklists`/
  `useGetOpenChecklists` (and the Issues equivalents) are fetched and merged together to get the
  complete current set of rows regardless of status, since a criterion might target any status, not
  just whatever Settings currently calls "ready." This reuses the existing ready+open split instead
  of adding a new unfiltered fetch (CxAlloy's Apps Script needs an explicit status filter either
  way — see the comment on `getOpenChecklists` in `src/lib/api.ts`).
- **Dashboard's Milestones widget and KPI row** read this same live computed data
  (`useMilestonesWithProgress` in `src/pages/arcapp/milestones.ts`) instead of the old hardcoded
  sample numbers, so neither can ever disagree with the Milestones page itself.
  - **Demand-driven fetching** (added 2026-10-30, after visiting the Dashboard got noticeably
    slower) — `useMilestonesWithProgress` used to always fetch Checklists/Issues/Submittals/NETA/
    Joint Pack Photos for every milestone's criteria, every time, on every page that shows
    milestone progress. Checklists/Issues in particular go through CxAlloy's Apps Script (cold-
    start + Sheets-read latency, the same cost that pushed the Equipment Tracker off live Apps
    Script calls entirely — see that section above), so a Dashboard visit was paying for up to five
    module fetches regardless of whether any milestone's criteria actually used them. Now it reads
    the (cheap, single-table) milestone records first, looks at which modules their criteria
    actually reference, and only fetches those — a project whose milestones only use Submittals no
    longer waits on Checklists/Issues/NETA/Joint Pack round trips on the Dashboard. The Milestones
    page itself passes `{ fetchAll: true }` instead, since its criteria *builder* needs every
    module's picker options available even before a criterion using that module exists.
- Any signed-in authorized user (`canEdit`, editor or admin — not admin-only, same as Submittals)
  can add, edit, or delete milestones and their criteria.

## RTFT — standalone logging + per-asset coverage

Same two additions as Tamper Seals got, applied to RTFT (`RtftTrackerPanel.tsx`):

- **Standalone logging**: `RtftSection.tsx` used to require a whole `ScheduleRow` (it read
  `row.asset` for the Equipment field) — generalized to take a plain `equipment: string` instead,
  the same way `TamperSealSection` was generalized earlier. The Activity Drawer usage just passes
  `activeRow.asset` now. **Log RTFT** in the RTFT Tracker's header opens the exact same form
  (Equipment/type/inspector/OFE/present flags/issues/L2 pass) with an `AssetPicker` — extracted
  into its own file since it's now shared between this and Tamper Seals — standing in for "which
  activity is this" so an inspection can be logged directly against an asset, no scheduled
  activity required.
- **Coverage badge**: every asset should have at least one RTFT entry — the header badge counts
  how many of `STY4dropdownoptions.Assets` have never shown up as an `equipment` value on any
  `STY4RTFT` row yet (hover it to see which ones), same pattern as Submittals' missing-coverage
  badge. There's no exempt-assets list for this one (wasn't asked for) — every tracked asset
  counts.
- **Once logged, an asset drops off the standalone picker's list** — the `AssetPicker` in the
  standalone form only ever offers assets from that same missing-coverage set, so it naturally
  shrinks as entries get logged (and clears back to empty after each submit, so the next pick
  starts fresh). Submitting the very last one collapses the picker into "Every tracked asset
  already has an RTFT entry logged."
- **The Activity Drawer's RTFT tab denotes — doesn't block — a pre-existing entry**:
  `RtftSection` fetches the RTFT list itself (same `useGetRtft()` the Tracker page uses) and shows
  a banner ("An RTFT entry already exists for … — see the RTFT Tracker page") whenever the
  activity's own asset already has one logged elsewhere, while still leaving the form usable —
  a legitimate re-inspection after a failed one still needs a new entry, so this only informs, it
  never disables submission.

## Asset Attributes (via LaunchPad's existing Google Sheet + Apps Script)

Ported from an older reference implementation of this same feature in **LaunchPad** — the sibling
app this Supabase project is shared with (see the sign-in section above). LaunchPad already has a
working "Asset Attributes" page backed by a Google Sheet full of nameplate/spec data per asset
(Manufacturer, Model, Serial #, delivery dates, etc.), read/written through `getEquipmentAttributes`/
`saveAttributes` actions on **the same shared Apps Script** ArcSite already calls for CxAlloy
Checklists/Issues (`getCxAlloyScriptUrl()` in `src/lib/api.ts` isn't actually CxAlloy-specific — it's
just "the STY4 project's shared script," stored in `launchpad_projects` and reused by LaunchPad for
a dozen other things too). That meant no new script or table was needed — `AssetAttributesManager.tsx`
just gives ArcSite its own window into data LaunchPad's version already reads and writes.

- **Gated by its own per-project Settings toggle** (added 2026-09-25) — Settings → "Asset
  Attributes enabled for this project" (`asset_attributes_enabled` in `arcapp_settings`,
  `assetAttributesEnabled` in `AppSettings`/`ShellContext`), gating the page/nav item the same way
  `netaTrackerEnabled`/`jointPackEnabled` do. Deliberately not tied to the `cxAlloyActions`
  capability Checklists/Issues use, even though it used to share that gate: `getEquipmentAttributes`/
  `saveAttributes`/`saveImageOnly`/`ocrImage` are pre-existing LaunchPad actions on the shared
  script, not an ArcSite addition to it, so a project can have Asset Attributes working while
  Checklists/Issues aren't wired up yet, or vice versa. `getCxAlloyScriptUrl()` in `src/lib/api.ts`
  is now a pure URL resolver with no capability check baked in; `fetchCxAlloySheet` (Checklists/
  Issues/CxAlloy Settings/People) and the new `getAssetAttributesScriptUrl()` (Asset Attributes)
  each gate it independently before calling. STY4 was seeded with this on to preserve its existing
  behavior; SAN-NT1B (and any new project) starts off.
- **Grouping**: each column header in the sheet is either a bare attribute name (falls under
  "General") or `"Group: Attribute Name"` (e.g. `"Nameplate: Manufacturer"`) — `groupAttributes()`
  splits on the first `:` and renders one section per group, matching LaunchPad's own convention
  exactly so the two apps' views of the same data look the same.
- **TBD highlighting**: a blank value or the literal text `TBD` renders with a red border, matching
  LaunchPad's "still needs a value" visual cue.
- **Saving**: only changed fields are sent (`{attribute, newValue}` pairs) via `saveAttributes`, and
  the Apps Script response's `debug` log array (used elsewhere in LaunchPad to report per-attribute
  write failures) is checked for `❌`/`ERROR` before treating a save as successful — mirrors how
  LaunchPad's own save handler decides whether to alert the user.
- **Multi-box photo-crop OCR** (`MultiBoxOcrModal.tsx`, opened via **Scan Photo** on each attribute
  group's header): take one photo of a nameplate (native camera via `capture="environment"`,
  same reasoning as the reference — "guarantees the best focus"), select an attribute from that
  group's button toolbar, draw a box around where it appears on the photo, repeat for as many
  attributes as the nameplate shows, then **Process N Boxes**. That:
  1. Draws one annotated copy of the full photo (every box outlined + labeled, with the same
     collision-avoiding label-placement logic as the reference so labels never overlap each other
     or the boxes) and uploads it via `saveImageOnly` as a Drive reference image.
  2. Crops + pads + white-backgrounds + contrast-boosts each individual box region into its own
     image and OCRs it separately via `ocrImage`, passing that upload's filename along so the
     script can associate the crops with their source photo.
  3. Drops each box's recognized text straight into its matching attribute field (not saved to
     the sheet until you hit the page's own **Save Changes**) — a box that comes back empty just
     doesn't fill anything in, it doesn't fail the whole batch.
  Uses Pointer Events (not separate mouse/touch listeners like the reference) for one code path
  that works with mouse, touch, and pen alike.
- **QR-code scanning** (html5-qrcode + a field-mapping UI) is still deferred — the photo-crop OCR
  flow was the piece asked for. It'd call the same shared script (no new action needed there,
  either) if it gets ported later.
- Verified live against the real script — 1,518 real assets loaded, a real asset's grouped
  attributes rendered correctly including a live TBD field, and the full box-draw → process →
  apply flow was exercised end-to-end with the write-side calls (`saveImageOnly`/`ocrImage`)
  mocked, confirming a drawn box correctly fills its attribute field. **No real photo was
  processed or saved against production** during verification, to avoid writing test data/photos
  under a real asset's name.

## Equipment Status Tracker (mirrors LaunchPad's own module)

ArcSite's view of LaunchPad's Equipment Status Tracker grid — the L2 Verification / L3 Functional /
L4 Integrated phase-tracking board, ported from LaunchPad's `equipment-tracker-view.js` shadow-DOM
component (`EquipmentTrackerPanel.tsx`, `EquipmentTrackerPdfModal.tsx`,
`EquipmentTrackerSettingsModal.tsx`, `lib/equipmentTracker.ts`) and restyled to fit ArcSite's dark
theme instead of copying LaunchPad's light-green one. Originally shipped read-only; as of
2026-10-29 the System Config + Phase Rules Engine editors are ported too, so this page is now a
full mirror rather than a read-only view.

- **Grid data has no new backend.** This still doesn't call Apps Script to *read* the grid — it
  reads `launchpad_equipment_tracker_data` and `launchpad_equipment_tracker_config` directly from
  Supabase, the same tables LaunchPad's own tracker reads. LaunchPad periodically syncs the
  underlying Google Sheet into the `data` table itself (a GitHub Action, not this app); both tables
  were already anon-readable and shared, so the read side needed zero schema/RLS changes.
- **Cards (default view, ARC-324)**: one card per asset, in columns by the phase it's in now: L2,
  L3, L4, Complete (a phase hidden in System Config gets no column). A card shows each phase's
  colored Overall Status with its open/total CHK or test count, plus the asset's open gating and
  non-gating issues; **Details** lists the gate CLs, the open CHKs/tests and the open issues, each
  linked. An asset sits in the first phase that applies and isn't finished; a phase counts as
  finished when its Overall Status matches a **Cx Complete** or **Closed** status in System Config
  (**Tests Closed** for L4), so the board follows each project's own status names. Blank, N/A and
  "No CL / No L4" phases are skipped. In this view the search box filters the cards, and an Area
  button opens the same Area filter as the grid. The Cards/Grid choice is remembered per browser.
  Columns draw 60 cards at a time with a "Show more" button. Code: `EquipmentStatusBoard.tsx` and
  `buildAssetCards` in `lib/equipmentTracker.ts`.
- **Grid**: sticky-header, horizontally + vertically scrolling table — frozen Asset/Area columns,
  then L2/L3/L4 phase groups (Gate CL column(s) + a colored Overall Status summary, each
  expandable to show every individual Support CL), then an Asset Issues group (colored open-issue
  summary, expandable to every individual issue). Cell colors come from the synced Phase Rules
  (matched against the status text) first, then the configured open/closed/cx-complete status
  lists.
- **Filtering**: click the ▼ on any of the 9 filterable columns (Asset, Area, each phase's Gate CL
  1 / Overall Status, Open Issues) for a searchable checkbox dropdown — cascading, so one column's
  available values narrow based on every other active filter, same as the reference.
- **Search**: a debounced global search box scans every field on every visible row, with a
  match counter and ▲/▼ navigation that scrolls to and highlights the current match (amber, not
  green — green is already used everywhere for phase-rule status colors) and auto-expands whatever
  phase/issues column the match was found in.
- **Export PDF**: a column-picker modal opens a plain print window built straight from the
  currently-filtered row data (not by scraping the rendered grid's DOM, unlike the reference) and
  calls the browser's print dialog.
- **System Config + Phase Rules Engine** (added 2026-10-29) — an admin-only **System Config**
  button opens `EquipmentTrackerSettingsModal.tsx`, a field-for-field port of LaunchPad's own
  Settings modal: phase names/headers + Gate/Support toggles per L2/L3/L4, the Global Issues
  header, nine status-color lists (Checklists Open/Closed/Cx Complete, Tests Open/Closed, Global
  Issues Open/Closed, Gating/Non-Gating severities), a fallback color, and the Phase Rules Engine
  table (Active/Phase/threshold expressions/Result Status/Color, add/remove rows).
  - **System Config saves as a plain Supabase upsert** to `launchpad_equipment_tracker_config` —
    those fields are pure display config this page already reads straight from there, so toggles/
    headers/status colors take effect immediately on save.
  - **Phase Rules are different, and need real care**: the actual rule *evaluation* that derives
    each asset's L2/L3/L4 status happens entirely server-side (Apps Script/Sheet-side — neither
    LaunchPad's nor ArcSite's own JS ever evaluates `maxGate`/`maxSupport`/etc.), keyed off the
    Sheet's own copy of this table, which is what the periodic GitHub Action sync then copies into
    Supabase's `phase_rules` column. Writing `phase_rules` to Supabase directly would be inert (the
    Sheet never actually changes) and would get silently reverted by the next sync regardless, so
    saving Phase Rules here **also POSTs the full settings payload to this project's own dedicated
    Equipment Tracker Apps Script** (a separate, per-project deployment bound to the Equipment
    Tracker spreadsheet — not the shared CxAlloy script) exactly like LaunchPad's own "Save & Sync
    to Sheet" button does. That URL is a new admin-editable Settings field on this page
    (`equipment_tracker_script_url` in `arcapp_settings` / `equipmentTrackerScriptUrl` in
    `AppSettings`/`ShellContext`), blank by default — until it's set, System Config still saves
    fine, but the modal shows an explicit notice that Phase Rule edits aren't syncing anywhere real
    yet, rather than looking like a silent success that reverts later.
- Verified live against real production data — 1,297 real assets loaded, phase-rule coloring
  correct, expand/collapse, cascading column filters (1,297 → 114 rows on an Area filter, cleared
  back to 1,297), global search (found and navigated 34 real matches, correct row highlighted),
  and a full PDF export exercised end-to-end (114-row filtered popup with correct headers/grouped
  CHK and issue ids) — from before this page gained a write path at all.

## To-Do — Teams & task assignment

To-Dos are no longer hardcoded sample data — they're real, persisted rows (`arcapp_tasks`), and
can be assigned to a **team** (`arcapp_teams`, a name + a `members` list of `{name, email}`) or to
a specific person. Both tables are wide open (`anon` + `authenticated`, no editor check), same as
Workflows — see `supabase/schema.sql`/`policies.sql`.

- **Manage Teams** lives at the top of the To-Do page (`TeamsManager.tsx`) — create/rename/delete
  teams, add/remove members. Deleting a team doesn't delete its tasks; they just fall back to
  unassigned (`ON DELETE SET NULL`).
- **My Tasks / All Tasks** toggle on the To-Do page, and the Dashboard's "Your To-Dos" widget,
  filter by matching the signed-in user's email against a task's `assigned_email` or the member
  list of its `assigned_team_id` (`isTodoMine()` in `utils.ts`). Signing in is only needed for
  that personalized view — creating/editing/assigning/completing tasks and teams needs no sign-in.
- The old sample-data To-Dos were carried over as real seed rows in `schema.sql` so the list isn't
  empty on first load.
- **Board view** (added 2026-10-30, made the default later the same day) — a **View: Board / List**
  toggle next to My Tasks/All Tasks switches between a fixed **To Do / In Progress / Done** Kanban
  board (`TodoBoard.tsx`, the default) and the original flat list, kept rather than replaced (same
  List/view-toggle pattern Joint Pack Photos' Asset List/Photo Gallery uses). A new `status` column
  on `arcapp_tasks` (`'todo' | 'in_progress'
  | 'done'`, backfilled from the existing `done` boolean — nothing could already be "in progress")
  is the real field now; `done`/`completed_at` stay in sync with it on every write
  (`setTaskStatus`/`setTaskDone` in `src/lib/api.ts`) so every pre-existing done/not-done consumer
  (the List view's checkbox, `KpiRow`, `TodoPanel`'s open count, `todoDueDisplay`) keeps working
  unchanged. Cards move between columns via **‹ / ›** buttons, not drag-and-drop — native HTML5
  drag-and-drop doesn't work reliably from touch on iOS Safari, and this app runs on iPad, so a
  button that always works everywhere beat a drag interaction that wouldn't (would need a
  touch-aware DnD library to do properly, which wasn't worth the new dependency for this).

### Checklist/Issue/NETA markers in "Your To-Dos" — summary cards + individually-assigned items

The To-Do page and Dashboard's "Your To-Dos" widget both surface two kinds of Checklist/Issue/NETA
markers, computed once by `useOpenItemsData()` (`OpenItemsTodoPanel.tsx`), called once in
`AppShell.tsx`, and handed down as `ctx.openItems` so neither page triggers its own fetch.

- **There is no browsable "Open Checklists/Issues/NETA ..." list on the To-Do page** (removed
  2026-09-24, by request — the Checklists, Issues, and NETA Tracker pages already list the real
  items; duplicating that as a fourth place to browse them wasn't needed). The To-Do module's job
  here is purely notification: tell the right person something needs their attention, and point
  them at the page where it actually lives.
- **Default assignee per category** — a team-or-person picker next to each category's toggle, on
  that category's own page's Settings drawer as of 2026-10-26 (used to be the main Settings tab)
  (`checklist_default_assignee_*`/`issue_default_assignee_*`/same for both NETA categories,
  3 keys each: `_team_id`/`_email`/`_name`, saved together via `saveDefaultAssignee` in
  `src/lib/api.ts`; the "specific person" option is a dropdown of `arcapp_authorized_users`, not
  free text — only someone who can actually sign in can usefully be a default assignee). When the
  default matches the signed-in user (directly or via team membership) and the category's count is
  above zero, they get a single roll-up card in "Your To-Dos" → My Tasks (`MySummaryCard`/
  `mySummaries` in `OpenItemsTodoPanel.tsx`) — e.g. "Issues need to be reviewed · 12". Clicking it
  navigates to that category's own page (`todoSummaryRoute`: Checklists → `/checklists`, Issues →
  `/issues`, either NETA category → `/netatracker`). The card disappears on its own once the count
  hits zero — nothing to dismiss or mark done.
- **What the count counts differs by category** (changed 2026-09-24 — it used to be "still open"
  for all four, matching what the removed list sections showed): Checklists/Issues count what's
  **ready for review** — the same `checklistReadyStatuses`/`issueReviewStatuses` Settings lists and
  `getChecklists`/`getIssues` calls the Checklists/Issues pages themselves use — since a reviewer
  cares about what's ready for them specifically, not everything outstanding project-wide. NETA
  categories are unchanged: still "still open" (Submissions: not yet Submitted to Google; Returned
  Files: not yet Uploaded to ACC), since NETA has no equivalent "ready" status to switch to.
- **Individually-assigned items** (`arcapp_item_assignments`, keyed by CxAlloy id / NETA document
  name) still fold into "Your To-Dos" → My Tasks as their own rows (`MyItemRow`) if any exist from
  before the browsable list was removed — a type badge (Checklist/Issue/NETA Submission/NETA
  Returned), a link back to the source, and a reassign chip (`AssignPopover`, same one used
  elsewhere). There's no remaining UI to create a *new* individual assignment now that the list
  sections are gone; this only keeps existing ones visible and reassignable.
- `arcapp_item_assignments` is wide open (`anon` + `authenticated`, no editor check) — same
  pattern as `arcapp_tasks`/`arcapp_teams`.

## Sign-in — a full-page gate, admins vs. editors, Google OAuth

**As of 2026-09-24, the entire site requires signing in.** `AppShell.tsx` renders nothing else —
no sidebar, no data, no routes, zero Supabase queries fired — until there's a real, authorized
session; `SignInPage.tsx` (a full page, not a dismissible modal — the old `SignInModal.tsx` is
gone) is all that's shown otherwise. This is a deliberate reversal of how the app worked before:
several features (Tamper Seals/RTFT logging, Joint Pack Photos, Workflows, To-Do) were previously
built to work without signing in at all, by explicit request at the time. That's no longer true for
any of them — being on the allowlist is now required just to see the app exists.

**Google is the primary sign-in option**, with the original magic-link email as a fallback. Either
way, the result is gated: `src/lib/useCurrentUser.ts` checks the signed-in email against
`arcapp_authorized_users` and immediately signs back out anyone not on it, surfacing why directly
on the sign-in page (no more small dismissible banner floating over content — there's no content
to float over now).

**Two roles, both on that same table** (`arcapp_authorized_users.role`, `'admin' | 'editor'`):
- **Admin** — can change Settings (every field there, plus the Authorized Users list itself).
- **Editor** — can do everything else (log Tamper Seals/RTFT, manage Workflows, review Submittals,
  reassign Checklist/Issue/NETA To-Do items, etc.) but Settings is entirely read-only for them —
  every field shows disabled with an "Only admins can change settings." hint.

Manage the roster (add/remove people, change roles) from **Settings → Authorized Users**, admin-
only. `saveAuthorizedUser`/`getAuthorizedUsers` in `src/lib/api.ts` carry the `role` column now;
`useCurrentUser.ts` reads it into `CurrentUser.role` at sign-in, and `AppShell.tsx` derives
`isAdmin`/`canEdit` from that alone.

**Which project(s) someone can reach — `allowed_projects`, added 2026-11-02.** Before this, being
on the roster at all meant full access to every project the Topbar switcher listed (STY4, SAN-NT1B,
RSE1A) — role only ever gated Settings, never which site's data you could see or touch. Now each
person in **Settings → Authorized Users** has a **Projects** picker (same All/toggle buttons as
every other multi-select filter in the app): **All** (the default — identical to today's behavior,
nothing to migrate) or a specific set. This is enforced in both places that matter:
- **Client-side** — `useCurrentUser.ts` reads `allowed_projects` at sign-in. If the project this
  browser last had selected isn't one of them, it redirects straight into one that is (via
  `setCurrentProject`) rather than showing someone else's data; if they're authorized for ArcSite but
  assigned to zero projects, sign-in is refused with a clear message instead of a silent lockout.
  `Topbar.tsx`'s project switcher only ever lists what `CurrentUser.allowedProjects` allows (and
  collapses to a plain label, no dropdown, if that's only one project).
- **Server-side** — every project-scoped table's authenticated-write RLS policy
  (`arcapp_settings`/`arcapp_tasks`/`arcapp_teams`/`arcapp_submittals`/`arcapp_workflows`/
  `arcapp_item_assignments`/`arcapp_milestones`) now also calls the new
  `arcapp_user_allowed_project(project_key)` SQL function, so a signed-in session can't bypass the
  switcher and write into an unassigned project just by calling Supabase directly — see the
  "per-project write authorization" block at the end of `supabase/policies.sql` (applied live
  2026-11-02; confirmed via `pg_policies` that all 7 tables' authenticated-write policies now
  reference the function). `anon`
  access (several of those tables are intentionally public/no-sign-in by earlier request — kiosk-
  style Workflows/Teams/Tasks/Item Assignments) is untouched — there's no email to check a roster
  against for an anonymous session, so that trade-off stands as it already was.
- Reads were deliberately left alone: most of these tables are already `anon`-readable site-wide (by
  prior, explicit requests — see each table's own section below), so restricting only
  `authenticated` reads would add complexity without closing anything real.

**Project picker at sign-in — `ProjectPickerPage.tsx`, added 2026-11-06.** Before this, anyone
allowed into more than one project (including every unrestricted/admin account, since
`allowed_projects = null` means "all of them") just silently landed in whatever project was last in
`localStorage` — STY4 by default — with no indication other projects existed short of finding the
Topbar switcher themselves. Now, right after a successful sign-in, if the signed-in person can reach
more than one project, they see a dedicated full-page picker (same visual shell as `SignInPage.tsx`)
listing every project they're allowed into, with whichever one was last used marked "Last used";
clicking one continues straight into the app. Someone restricted to exactly one project skips this
entirely, same as before.

This happens **once per browser session, not once per page load** — `useCurrentUser.ts` tracks it
via `sessionStorage` (`arcapp_project_confirmed`, cleared on sign-out), not `localStorage`, so
switching projects later from the Topbar (which reloads the page) or just refreshing the tab doesn't
re-prompt, but closing the browser and signing in again later does. `confirmProject(key)` either
calls the existing `setCurrentProject(key)` (a project switch — reloads the page) or, if they picked
the project that was already current, finishes sign-in in place with no reload at all.

**Bulk Add** (added 2026-10-25, `AuthorizedUsersManager.tsx`/`bulkAddAuthorizedUsers` in
`src/lib/api.ts`) — a collapsible textarea next to the one-at-a-time form for pasting many people
at once, one per line: `email`, `email, name`, or `email, name, role` (comma- or tab-separated, so
a column pasted straight out of a spreadsheet works unchanged; a trailing role only counts if it
actually reads "admin"/"editor", otherwise a default-role dropdown above the textarea applies).
Deliberately **add-only, not upsert** — an email already on the roster is left completely
untouched (role, name, everything) rather than silently overwritten by whatever the pasted list
happened to say for them, since a bulk list someone pastes in may not even be thinking about roles
for people already added; the result message reports how many were added vs. skipped (already on
the list, listed by email) vs. ignored (no `@`) so nothing is silently dropped.

**Reading the full roster is admin-only** (`authorized_users_select_admins` in `policies.sql`) —
narrowed back 2026-11-03. It was widened 2026-09-25 to "any signed-in user" so every "assign to a
specific person" control in the app — Teams' member picker, a task's/Checklist-Issue-NETA-item's
assign-to popover, Settings' default-assignee picker — could offer a dropdown instead of free-text
name/email entry. That stopped being a safe thing to widen once `role` and `allowed_projects`
(above) existed: those are exactly the columns an editor shouldn't be able to read about every
other person on the roster, even though the Settings screen that shows them was already admin-only
in the UI (`AuthorizedUsersManager`'s `canEdit` prop is actually `isAdmin` — see `SettingsPanel.tsx`)
— the gap was that nothing stopped a signed-in editor from reading the raw table directly (e.g. from
the browser console).

The assignment controls above still need *some* roster to pick a person from, regardless of role,
so they go through `arcapp_authorized_users_directory()` instead — a `SECURITY DEFINER` SQL function
(same trusted shape as `is_arcapp_admin()`/`is_arcapp_authorized()`) that hands back only
`id`/`email`/`name`, and only to a caller who's themselves on the roster at all. `PersonSelect.tsx`'s
`useAuthorizedUsersOptions` and `DefaultAssigneePicker.tsx` both call it via
`useGetAuthorizedUsersDirectory()`/`PersonOption` in `src/lib/api.ts`; `AuthorizedUsersManager.tsx`
(the admin-only management screen itself) is the one remaining caller of the full
`getAuthorizedUsers()`/`AuthorizedUser` (role + allowedProjects included), which now only ever
succeeds for an admin anyway, matching the RLS. *Writing* to the roster (add/remove/change role/
change project access) is still admin-only, unchanged.
- A previously-saved assignment whose email is no longer on the roster still shows, selected and
  savable as-is, flagged "— not in Authorized Users" rather than silently disappearing (same
  stale-value pattern `CxAlloyStatusPicker` already used for status lists).

**Deliberately, completely independent of LaunchPad's `STY4authorized_editors` table** — that table
has its own separate `is_admin`/`role` columns, but they mean something different (LaunchPad's own
edit rights) and this was built to have zero dependency on it, in either direction. This used to be
a bigger gap than just the client-side check: several RLS write policies (`arcapp_settings`,
`arcapp_workflow_items`, `arcapp_submittals` + its storage bucket, and `arcapp_authorized_users`
itself) were checking `STY4authorized_editors` server-side — meaning the actual database security
boundary disagreed with whatever the new ArcSite-only role said. All of those were migrated to check
`arcapp_authorized_users` instead (self-referentially, in that table's own case) as part of this
change — see `supabase/policies.sql`. `arcapp_authorized_users` was seeded with exactly one admin
(not bulk-imported from `STY4authorized_editors` this time, to keep the roster genuinely
ArcSite-owned) — add everyone else via the new Settings UI.

**Google sign-in needs one-time setup this repo can't do for you** — `supabase.auth.signInWithOAuth({ provider: 'google' })`
is called from the app, but nothing happens until:
1. **Google Cloud Console** → create an OAuth 2.0 Client ID (Web application). Authorized redirect
   URI: `https://rcnxetcomdrlxvlarqoc.supabase.co/auth/v1/callback`. Authorized JavaScript origins:
   `http://localhost:5173` and `https://arc-app-umber.vercel.app` (the deployed app — add any
   Vercel preview-deployment URLs too if you ever sign in from one of those).
2. **Supabase Dashboard** → Authentication → Providers → Google → paste that Client ID/Secret,
   enable the provider.

Until that's done, clicking "Sign in with Google" will fail with an error from Supabase (shown in
the modal) — the magic-link fallback keeps working in the meantime, so sign-in isn't blocked on it.

**This Supabase project is shared with LaunchPad**, so its Auth redirect allow-list defaults to
LaunchPad's URL — without ArcSite's own URL added there too, either sign-in method bounces back to
LaunchPad instead of ArcSite after completing. Add these to **Authentication → URL Configuration →
Redirect URLs** (alongside LaunchPad's existing entry, not replacing it):

```
https://arc-app-umber.vercel.app
https://arc-app-umber.vercel.app/**
http://localhost:5173
http://localhost:5173/**
```

Leave **Site URL** as LaunchPad's — it's just the fallback when a `redirectTo` isn't on the allow-
list above, and both sign-in paths here already pass their own (`window.location.origin`).

**Verified client-side** with a faked signed-in session (real Google OAuth needs a browser flow
this can't automate) across four scenarios: signed out entirely (only the sign-in page renders,
confirmed zero Supabase queries fire — not just zero visible UI); signed in as an editor (full app
renders, Settings shows the read-only hint with every field disabled); signed in as an admin
(Settings fully editable, Authorized Users list shows and lets you change roles); signed in but not
on the allowlist (sign-in page shown again with the "isn't authorized" message, not the app). All
four matched exactly. A production build was also run clean after the change.

**That faked-session testing missed a real server-side bug**, because faking the session mocks the
Supabase REST layer entirely and never exercises real Postgres RLS evaluation. The first actual
Google OAuth sign-in failed with `infinite recursion detected in policy for relation
"arcapp_authorized_users"` — every write policy above (`settings_write_admins`,
`workflow_items_write_authorized`, `submittals_write_authorized`, the submittals storage-bucket
policies, and `authorized_users_write_admins` itself) had been written as a raw
`EXISTS (SELECT 1 FROM arcapp_authorized_users ...)` subquery, and Postgres re-applies that table's
own RLS policies every time any policy's subquery selects from it — including the subquery inside
`arcapp_authorized_users`' own policy, which recurses forever. Fixed by moving the check into two
`SECURITY DEFINER` functions (`is_arcapp_admin()`, `is_arcapp_authorized()` — SECURITY DEFINER runs
as the function owner and bypasses RLS inside the function body, so the lookup no longer re-enters
the calling policy) and pointing every affected policy at one of those instead of an inline
subquery — see the top of `supabase/policies.sql`. Confirmed live via `pg_policies` that all 7
affected policies now reference the functions and no raw self-referential subquery remains. Real
Google sign-in has not yet been re-confirmed end-to-end after this fix — that still needs a live
retry.

## Workflow items

The Workflows builder reads its list of on-site modules from `arcapp_workflow_items`
(`supabase/schema.sql` — already applied), not a hardcoded list. Manage the catalog from
Settings → Workflow Items: add, rename, enable/disable, or delete entries there. Order is **not**
set there — each workflow sets its own item order when it's built (the "Order shown on-site" drag
list in the workflow form). `src/pages/arcapp/workflowItems.ts` holds a fallback list used only if
the table can't be read (logs a console warning when that happens).

Each row has a `config jsonb` column reserved for the definition of what the item should actually
do. Five items have hand-written forms in `ActivityDrawer` (`late_time_personnel`, `tamper_seal`,
`joint_pack_photos`, `rtft`, `cmms_data_collection`); `equipment_photos` and `scaaf_study` render a
"not configured yet" placeholder until their behavior is specified. `launchpad_status` was removed
— its schedule-status info duplicated the always-present Activity Result field.

## ⚠️ Security — read before deploying

Inside Retool, every database call ran through a privileged server-side connection your users
never touched. Once this ships as a plain client-side app, **the Supabase anon key is public** —
it's sitting in the JS bundle anyone can view. From that point on, the only thing standing between
"anyone on the internet" and your data is **Row Level Security (RLS) policies** in Postgres, not
anything in this app's code.

We set up RLS for the two tables this migration created:
- `arcapp_workflows`, `arcapp_settings` — readable by any authenticated user, writable only by
  emails present in `STY4authorized_editors` (`supabase/policies.sql`, already applied).

We did **not** change RLS on the pre-existing tables (`STY4Assets`, `STY4BackEndData`,
`STY4authorized_editors`, `STY4dropdownoptions` already have RLS on; `STY4RTFT` and
`STY4Submittals` currently have RLS **off**) because another app (LaunchPad) shares this database
and we don't know what it expects. Before going live:

1. Check the existing policies on `STY4Assets`, `STY4BackEndData`, `STY4dropdownoptions`, and
   `STY4authorized_editors` in the Supabase dashboard (Auth → Policies) — confirm they allow what
   this app needs (`authenticated` read on all four; `authenticated` + editor-only write on
   `STY4Assets`/`STY4BackEndData`).
2. Decide what to do about `STY4RTFT` having RLS **disabled** — right now that means anyone with
   the anon key can read/write it with no restriction. (`STY4Submittals` has the same problem, but
   this app no longer reads or writes it at all — see above — so it's only a concern if something
   else still depends on it.) Commented-out policies matching the pattern used elsewhere are in
   `supabase/policies.sql` — coordinate with
   whoever owns the LaunchPad app before flipping this on, since enabling RLS with no matching
   policy will break existing access.
3. Supabase Auth: this app assumes `auth.jwt() ->> 'email'` matches an email in
   `STY4authorized_editors`. If you turn on email confirmation, custom domains, or SSO, make sure
   the JWT still carries a matching `email` claim.

## Color palette — re-tuned to the org's shared Design System

ArcSite's whole dark theme was re-tuned 2026-11-02 to the "Design System" Artifact shared in the
organization (its `project/tokens.css`), replacing the previous from-scratch palette.

- **Single-accent structure kept, by request.** The design system actually specifies Petrol
  (`#0f5a60`, a dark teal) as the primary button/link color and reserves its "Arc Green"
  (`#4ebd4f` — literally named for this app) for focus rings and selections only. Adopting that
  split would have meant deciding where Petrol shows up everywhere green currently does — a much
  bigger identity shift away from ArcSite's current all-green sci-fi look. Instead, `--green` (and
  `--green-soft`/`--green-dim`/`--green-deep`, all derived from Arc Green) stays the single accent
  everywhere it already was — only the exact shade changed, not the structure.
- **Neutrals** (`--bg`/`--bg-elev`/`--border`/`--text`/etc.) moved from ArcSite's old cool blue-black
  scale to the design system's warm charcoal one (its dark-mode `Page`/`Surface`/`Border` tokens).
  This is the one part of the change that alters the app's overall mood more than the green swap
  alone would — say if the warmer neutrals read wrong next to the still-blue starfield background
  dots (`.starfield` in `src/arcapp.css`, deliberately left untouched — they're decorative, not part
  of the token palette).
  - The design system only defines three dark-mode neutrals (`Page`, `Surface`, `Border`) — it has
    no dark equivalent for several tokens ArcSite needs (`--bg-elev-2`, `--border-strong`,
    `--text`/`--text-muted`/`--text-faint`). Those were derived rather than invented from nothing:
    `--text` reuses the design system's light-mode `Page` color (#f3f2ee), mirroring how its own
    light-mode `Textprimary` already equals its dark-mode `Page` (#141718) — i.e. text and page
    swap value between modes in the source system, so dark-mode text follows the same relationship;
    `--bg-elev-2`/`--border-strong` continue the arithmetic step already visible between the design
    system's `Page`→`Surface`/`Border` values; `--text-muted`/`--text-faint` are lightened versions
    of its light-mode `Textsecondary`/`Textdisabled` (too dark to read on a dark background used
    as-is) tuned to sit clearly between `--text` and `--border-strong`.
  - **Amber/red** (caution/hold status colors) switched to the design system's workflow status
    colors — its "in progress" chart color (`#f2c94c`) and "failure" chart color (`#ee8080`) — the
    closest semantic match to ArcSite's existing caution/critical usage, rather than inventing new
    ones.
- **Everywhere this needed changing**: the token block in `src/arcapp.css`, the brand-mark SVG
  gradient (`Topbar.tsx`, `SignInPage.tsx`, `public/icon.svg`), the hardcoded fallback colors in
  `App.tsx`'s "Supabase isn't configured" screen and `ErrorBoundary.tsx` (both render outside the
  main stylesheet's reach during a startup/crash state, so they carry their own copies of the same
  values rather than reading CSS variables), `statusColor()` in `utils.ts`, and the
  `DEFAULT_MILESTONE_STATUS_STYLES` fallback in `src/lib/api.ts` (only the *default* — any project
  that already customized its milestone status colors via Settings keeps what it saved).
  - `public/icon.svg`'s gradient changed, but the **rasterized PNGs don't regenerate
    automatically** (`apple-touch-icon.png`/`icon-192.png`/`icon-512.png`/`favicon-32.png` — see
    the iPad section below) — those still need a manual re-export from the updated SVG.
- **Typography and spacing weren't touched** — the request was specifically about the color
  palette, and the design system's Roboto-everywhere type scale would have meant losing ArcSite's
  distinctive Orbitron display font, a bigger change than was asked for.

## iPad support & app icon

The app is usable as a full-screen, installable iPad app, not just in Safari's browser chrome:

- **`public/icon.svg`** is the source icon (the same arc mark as the in-app topbar logo, on a
  dark rounded-square background). `public/apple-touch-icon.png`, `icon-192.png`, `icon-512.png`,
  and `favicon-32.png` are rasterized from it — regenerate them with a headless-browser screenshot
  (or any SVG-to-PNG tool) if `icon.svg` ever changes; there's no build step wired up to do this
  automatically.
- **`public/manifest.webmanifest`** + the `apple-mobile-web-app-*` meta tags in `index.html` mean
  "Add to Home Screen" on iPad launches ArcSite full-screen (no Safari address bar), with the arc
  icon and "ArcSite" as the name.
- **`src/arcapp.css`** has a `max-width:860px` breakpoint (shared with the sidebar-to-top-nav
  layout switch) that also: bumps form input/select font-size to 16px (Safari zooms the whole page
  in on focus of anything smaller — this keeps desktop inputs at their normal, denser size while
  avoiding that on iPad/phone widths), enlarges the nav-pill touch targets to ~44px, and hides the
  topbar tagline so the header doesn't crowd on a portrait iPad. `touch-action:manipulation` and
  `-webkit-tap-highlight-color:transparent` are set globally so taps register immediately instead
  of waiting ~300ms for a possible double-tap-to-zoom, and without the gray tap-flash.
- Below 860px wide the sidebar becomes a horizontally-scrollable top nav (portrait iPad); above it,
  iPad landscape gets the same persistent left sidebar as desktop.
